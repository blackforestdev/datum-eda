I · owned-window contract
Global Preferences is a native input-modal child of its Datum window
Window kinda real native window, not an in-canvas panel — the title bar and its close action belong to the desktop, not to Datum
Modalityinput-modal to its owner: input to that Datum window is blocked while it is open, and Tab never leaves it
Waylanduses the xdg_toplevel parent relationship to declare its owner; the compositor keeps it stacked above that owner
Stackingabove its Datum owner only. Unrelated applications may sit above both — the user’s window manager stays in charge
Nevernever globally always-on-top; it does not float over the user’s whole desktop
Savingchanges save immediately, so there is nothing to confirm, apply, or discard on close
Inheritancefuture immediate-save Datum Preferences windows inherit this posture unless a later owner decision introduces staged transactions
Why there is no in-content Close. The window is owned by the desktop and saves as you go, so a Close, Apply, OK or Cancel button would be a second, redundant way to do what the title bar already does — and Apply or Cancel would imply staged edits that do not exist. Explanation Close remains because it closes only the resolver explanation, not the window.

The persistence boundary
Persistedpreference values, saved immediately, and their changed-or-reset provenancea value set to 10 s is still 10 s, and still reads "set by you", after close and reopen
Not persistedsearch query, filtering, open choice, open explanation, transient notice, internal focusthese are window-view state, not preferences, and are never written to the store
Why it mattersa stale query or a half-open explanation restored from a previous session would misrepresent what the window is showing
Search is not a preference. Everything a user deliberately sets survives; everything the window happened to be doing does not. That line is worth stating because immediate saving makes it easy to assume the whole window is persisted — it is not, and reopening is always the same clean Appearance state.

Seven controls, seven contracts. Angle notation and Angle precision are two separate controls with two accessible entries and two focus stops — one selects the notation, the other offers only that notation's precision inventory. Every control announces its stored value and, where they differ, its resolved value, so a screen-reader user is never told "follow system" without learning what it currently resolves to. The window and search entries are included so this inventory is self-contained.
Scope boundary. This is Global Preferences: it edits the six global descriptors and nothing else. No Project-policy editing and no document-unit editing appears here. A change seeds a copy into new Projects at creation, with a durable itemized receipt written by the Project mutation authority; existing Projects never follow a later Global change, and a Global edit leaves open Project files byte-identical. The Project-scoped preferences surface is separately specified and is not authorized by this target.
Status. This is an open UNIT-I02R owner-review target. It does not authorize UNIT-I03 implementation and claims no production acceptance. Its controlling contract is Product Mechanics 040 — Project Working Units Authority (commit 97b0766), with the UNIT-I03 reconciliation contract in research/preferences-system/GP_SHARED_UNITS_ENGINE_REQUIREMENT.md as its non-visual detail; the separated future comparative catalog below is not implementation authority.
