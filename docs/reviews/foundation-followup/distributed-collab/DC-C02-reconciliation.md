## §B — MODEL-AUTHORITY (:57-61): the distinct collaboration authorities over one resolved model
The distributed architecture introduces NO new design authority and NO second commit path. It adds coordination authorities that sit AROUND the PM001/PM007 model, each with a stated must / must-not boundary; the resolved `DesignModel` remains the sole design authority (CLAUDE.md "resolved model is the authority"; not "a replica is authority").

| Authority | MUST | MUST-NOT |
|---|---|---|
| **Project** (PM007 :140-158, EXTENDED) | own identity/storage-layout/active-model/workspace refs; gain a replica-set identity (which replicas of this Project exist) | own design bytes; become a network service |
| **Replica / checkout** (NEW coordination authority, EXTENDS PM007) | name one local materialization of a Project's SourceAuthorityState + journal on one site/machine; carry its own replica id + last-synced revision frontier | be a rival DesignModel authority; write source shards except through the one commit path (PM001 :316-333 / PM007 :193-194) |
| **Workspace** (PM007 :196-214, UNCHANGED) | own interactive session state; own `workspace_revision`; degrade on missing objects | hold design authority; write source shards; be synced AS design state |
| **Changeset** (NEW view over PM001) | name a coherent set of `Transaction`s/`OperationBatch`es for exchange/review | be a new mutation primitive; bypass `commit()` |
| **model-revision / object-revision** (PM001 :302-314, PM053 NetId, UNCHANGED) | be the identity spine a merge reconciles | be reconciled by textual proximity (C-DVCS-2) |
| **live-session** (NEW, optional) | name a transient presence/co-edit session | be design authority; be a prerequisite for local function (C-LF-1) |
| **merge / review** (NEW, over PM001 Proposal :131-157) | adjudicate divergent changesets into accepted Transactions | commit un-reviewed remote bytes; be a side-door writer |
| **permission** (NEW, PREPARED for owner) | gate who may propose / accept / release | substitute for semantic validity or a signature (§G) |
| **release** (PM034, CONSUMED, §H) | consume PM034 controlled-release/issued identity | invent a rival release lifecycle (PM034 :102) |

**Invariants preserved verbatim-in-spirit (:60-61 → PM001 :316-333):** ONE resolved model; typed Operations; inspectable Diffs; the ONE canonical mutation path. Presence/workspace state is kept SEPARATE from design authority (:59-60 → PM007 :193-194/:209): a live-session or workspace never writes a source shard. **No new authority owns a private writer or a second commit path** — every accepted change, local or merged-from-remote, still resolves to typed Operations through `commit()`.

## §C — STORAGE-ATOMICITY (:63-67): Git-compatible serialization + cross-shard semantic atomicity
- **Deterministic Git-COMPATIBLE shard serialization.** The deterministic JSON shards (PM001 :330) already serialize to stable, line-oriented, content-addressable bytes — *compatible* with Git/content-addressed transport as a FORMAT discipline. **This is NOT a selection of Git as the transport** (that is DURABLE/§D, owner-reserved); compatibility ≠ dependency (PM029). 
- **Stable identity allocation.** New objects across replicas must allocate globally-stable identities that never collide on merge — building on PM053 (NetId final-state atomic nomination/fallback) and PM001 object identity. **CONSTRAINT (C02-ATOM-1):** identity allocation must be collision-free across disconnected replicas. Candidate schemes PREPARED for owner at §J (not selected): **(a)** site-scoped id spaces; **(b)** content-addressed ids; **(c)** provisional-local-then-reserve-at-sync. **C-LF-1 tension noted on (c):** a *pure* central-reservation-at-sync scheme would violate the no-central-dependency requirement (a disconnected replica could not allocate at all), so (c) is only coherently preparable in a provisional-local-allocation-reconciled-at-sync form that preserves offline allocation; the pure-central form is not viable under C-LF-1. (Same disclose-don't-decide discipline as the PM029 notes on O-D1/O-L2/O-S1.)
- **Cross-shard semantic atomicity/validation.** Promotes DC-C01 C-DVCS-1/C-DVCS-2 into a spec invariant, anchored on PM000D: a commit (local or merge-accepted) writes across shards atomically through ONE journal append + atomic rename + directory fsync (PM000D :374-393); an interrupted exchange rolls forward/back deterministically (:835-836); a split/incoherent replica opens in recovery/diagnostic mode, never accepted truth (:389-390/:750; PM007 ProjectManifest :164-168). 
- **The hard invariant (:66-67):** transport or text merge must NEVER silently publish an incoherent accepted design. **CONSTRAINT (C02-ATOM-2):** a merged changeset is re-resolved by the `ProjectResolver` and must pass the same validation as any commit before acceptance; a result that cannot be resolved "opens in recovery mode rather than silently accepting partial truth" (PM000D :388-390 — the direct recovery-mode law). The corroborating principle "pending/mismatch must never be published" (PM000D :944) holds here too, though its native context is the cross-domain Net-selection/identity path. A textual/transport merge that does not re-resolve is refused to recovery mode, not accepted. (This is C-DVCS-1/2 carried, not softened.)

## §D — DURABLE-MECHANISM (:69-73): the durable revision/replica/offline-exchange mechanism — PREPARED, NOT SELECTED
The durable layer governs how a replica's SourceAuthorityState + journal persist, diverge, and replay offline. The architecture SPECIFIES the requirements and PREPARES exact owner options; **it selects none.**
- **Requirements:** full local + disconnected functionality with no central dependency (C-LF-1); identity/revision relationships preserved across replicas (PM001 :302-314 + PM053); deterministic, reproducible replay of a journal on any replica (PM000D journal-cursor replay :390-393); divergence recorded, not lost.
- **Owner options PREPARED (→ §J / DC-C04):**
  - **O-D1 Git-as-substrate** — adopt Git itself as the content-addressed transport/store for shards+journal. *Pro:* proven distribution/integrity. *Con:* a third-party dependency (PM029 ratification required); textual-merge must be disabled in favor of semantic re-resolution (§C).
  - **O-D2 First-party content-addressed store** — Datum's own deterministic shard/journal store with content hashes, Git-compatible on export. *Pro:* no dependency; full control of semantic merge. *Con:* more first-party work.
  - **O-D3 Hybrid** — first-party semantic layer, Git optional as one transport among several (bundle, filesystem, http).
- **:73 explicit:** "A Git-like foundation is a CANDIDATE to evaluate, NOT already selected by this plan." **FINDING F-DVCS-1 (DC-C01) stands:** the transport-substrate dependency is an owner decision at DC-C04 under PM029; the semantic-merge layer (§C/§F) is first-party regardless of which transport is chosen.

## §E — LIVE-MECHANISM (:75-80): optional live collaboration/presence and its boundary with durable truth
- **Scope:** an OPTIONAL live layer for simultaneous compatible editing + presence, degrading cleanly to disconnected operation. **Boundary (hard):** the live layer is NEVER design authority and NEVER a prerequisite for local function — "full local functionality must not depend on… presence or connectivity" (bound :40-41 / C-LF-1). A Google-Docs-like UX or a central server is explicitly NOT required (:77-79); live is an accelerant over the durable truth, not a replacement for it.
- **Relationship to durable truth:** live edits are provisional until they land as Transactions through the one commit path (PM001 :316-333); presence/cursor/selection state is workspace-class, not source-class (PM007 :196-214 / §B). Disconnection degrades a live session to independent local journaling (§D), reconverged by merge (§F) — no data loss, no central arbiter.
- **:79-80 explicit:** the synchronization algorithm is NOT decided by implementation convenience and the optional live layer is NOT treated as design authority. **Owner options PREPARED (→ §J):** O-L1 operational-transform, O-L2 CRDT-backed live buffer reconciled to typed Operations on commit, O-L3 presence-only (no shared live buffer; single-writer-at-a-time within a session). **No selection here** — each is an exact owner choice with its dependency/complexity noted (a CRDT library would be a PM029 dependency).

## §F — CONFLICT-MECHANISM (:82-86): semantic merge/review, concurrent-writer authority — single-writer safety PRESERVED
This is the direct home of DC-C01 **C-DVCS-3 / Q6**. The architecture specifies the conflict/merge surface and PREPARES concurrent-writer options; **it preserves the current single-writer safety until DC-C04 explicitly ratifies a replacement, and it does not touch the PWO boundary.**
- **Surface specified:** conflicting-edit detection; semantic merge/review of divergent changesets (replay/merge typed Operations with identity reconciliation via PM053, C-LF-2); claims/locks; conflict visibility + resolution; **no-loss cancellation/recovery**.
- **No-loss recovery = compensating-journal law, NOT history rewind (PM000D :391-393):** a cancelled/rejected merge is undone by a NEW append-only compensating transaction (tagged `InverseBatch`) that advances revisions and stays auditable — never a decrement, rewind, or deletion of journal history. Any "rollback = rewind" reading is explicitly rejected here.
- **C-DVCS-3 / Q6 honored (hard):** distributed concurrent-writer coordination **EXTENDS** the PWO single-writer boundary (the single commit path PM001 :316-333 is enforced today under the LOCAL `ProjectWriteLease`, whose local contract is parked at PWO-C03, O1-R unresolved). This step **does not assume PWO resolved and does not alter the local single-writer contract.** **CONSTRAINT (C02-CONF-1):** current single-writer safety is preserved until DC-C04 ratifies a concurrent-writer model; the PWO→DC ordering is an explicit prerequisite (DC-C04 presupposes/sequences after PWO-C03). 
- **Owner options PREPARED (→ §J):** O-C1 pessimistic claims/locks (extends the lease to replica scope; insufficient alone for offline divergence, C-CAD-1); O-C2 optimistic semantic merge with review-gated acceptance; O-C3 hybrid (claims for live, semantic merge for offline divergence). **No concurrency/merge model selected.** The exact conflict taxonomy (which Operation pairs commute/conflict; how identity splits/merges reconcile) is **F-CAD-1**, carried as a DC-C04-prepared design target — recorded OPEN, not faked closed.

## §G — SECURITY-MECHANISM (:88-92): permissions, trust, provenance, signed exchange — four-way separation
- **Specified:** permissions (who may propose / accept / release); trust boundaries between replicas/sites; provenance + audit (PM001 Provenance on every Transaction; PM000D append-only auditable journal); signed exchange + verification across remote AND air-gapped sites (self-contained signed bundle of shards+journal+provenance, verifiable on arrival); adversarial/malformed-input + failure behavior (a malformed/forged bundle is refused atomically and opens in diagnostic mode, never partially accepted — PM000D :944 / §C C02-ATOM-2).
- **The hard line (:91-92), four-way separation — no clause collapses these:**
  1. a transport **signature** proves only origin/integrity of bytes;
  2. **permission** proves only that an identity is authorized to propose/accept/release;
  3. **semantic validity** is proven only by `ProjectResolver` re-resolution + validation (§C);
  4. **release approval** is proven only by the PM034 release authority (§H).
  **CONSTRAINT (C02-SEC-1):** a signature alone is NEVER described as permission, semantic validity, or release approval; each gate is independent and all required in their own right. 
- **Owner choices PREPARED (→ §J):** O-S1 signing/key-trust model (web-of-trust vs PKI vs project-rooted keys — any external crypto library is a PM029 decision); O-S2 permission/role model; O-S3 egress policy for any MCP/network side-effect (ties to the governed data-egress gate). **No selection here.**

## §I — CONFORMANCE-IMPACT (:100-106): obligations + failure cases for every operating mode
**Future proof obligations (SPECIFIED, not performed — :104-106):** for each named operating mode, the proof the eventual implementation must satisfy for ordinary manual use + all shared entry surfaces:
- **Compatible edits** (two replicas, non-overlapping): both merge via typed-Operation replay; result re-resolves coherently; provenance of both preserved.
- **Conflicting edits:** conflict detected, surfaced, review-gated; no silent loss; cancellation via compensating transaction (§F).
- **Offline divergence:** disconnected replicas each journal locally (C-LF-1); reconverge by semantic merge preserving each branch's provenance (C-LF-2); no central arbiter required.
- **Semantic validation:** every accepted/merged change passes `ProjectResolver` re-resolution (§C C02-ATOM-2); incoherent result refused to recovery mode.
- **Interrupted cross-shard exchange:** rolls forward/back deterministically (PM000D :835-836); partial state never accepted.
- **Stale/unauthorized input:** stale-revision rejected with reconciliation; unauthorized (permission/signature-failed) refused atomically (§G).
- **Audit:** every change, merge, and release is append-only + provenance-bearing (PM001/PM000D), reconstructible across replicas.
- **Recovery:** compensating-journal law only (§F); no history rewind anywhere.
- **Security + dependency/license + migration + roadmap impact documented:** security per §G; **dependency/license** — the durable transport (§D O-D1 Git), any CRDT (§E O-L2) or crypto (§G O-S1) library is a PM029 owner decision, NOT assumed; **migration** — existing single-replica Projects open unchanged and gain a replica identity only on explicit owner-authorized action (migration DESIGN here, not EXECUTION); **roadmap** — implementation is a separately-authorized successor after DC-C04/DC-C05.
- **:106 discipline:** this is a future proof specification, NOT permission to execute a proof slice or add a dependency. **Mandatory clauses left OPEN (not faked closed):** F-CAD-1 the exact conflict taxonomy (§F); the DC-C04 mechanism/transport/concurrency/live-sync/release selections (§J); these are carried OPEN to the owner, not resolved here.
