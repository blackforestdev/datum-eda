## §B — RESEARCH-DVCS: what Datum must validate ABOVE Git transport
**Proven DVCS capabilities (prior art, planning altitude):** content-addressed immutable object storage + a DAG of commits (Git); distributed clone/push/pull with no central authority required for history integrity; cryptographic content integrity (SHA object IDs); patch-theory / commutative patches (Darcs, Pijul) and operation/CRDT logs as alternatives to snapshot-diff. These are PROVEN for their domains.
**The textual-merge assumption to separate out:** Git (and line-diff tooling) MERGES textually — a 3-way line merge of two branches. **This assumption does NOT hold for Datum's authored design state.** Datum's canonical authority is the `DesignModel` resolved from deterministic JSON shards (PM001 :80-89, :330); a line-level textual merge of two shard versions can produce a syntactically-merged file that resolves to an INVALID or incoherent DesignModel (broken net identity, dangling references, two conflicting Operations silently interleaved). Textual coincidence is not semantic correctness — the same lesson as the NCC F4/F7 "coincidence ≠ identity" layer split.
**What Datum must validate above Git transport (anchored on PM001):** the merge/sync unit is the SEMANTIC layer, not text —
- Datum already HAS a semantic change log: the append-only journal of typed `Transaction`s, each a reviewed `OperationBatch` of typed `Operation`s with `Provenance` + `Diff` (PM001 :159-167, :91-118). This is richer than a Git textual diff and is the natural distributed-merge unit.
- The single commit path (PM001 :316-333) is the invariant a distributed model must preserve: a merged/synced change from a remote peer must still arrive through `commit()` (one place bytes change, one place the journal grows) — a sync must NOT be a private side-door writer (that would reintroduce exactly the retired-bypass defect PM001 :335-351 forbids). **CONSTRAINT C-DVCS-1:** remote/merged changes replay as typed Operations through the canonical commit path, not as raw shard-byte merges.
- model_revision / object_revision (PM001 :302-314) + stable NetId (PM053) are the identity spine a merge must reconcile: two divergent branches that both advanced revisions / renamed-split nets need SEMANTIC reconciliation (deterministic survivor, recorded transitions), not a textual pick-one. **CONSTRAINT C-DVCS-2:** semantic merge resolves identity/topology via the governed identity law, never by textual proximity.
- Git (or any content-addressed transport) is usable as a TRANSPORT/storage substrate for the deterministic shards + journal, but is NOT the merge authority. **FINDING F-DVCS-1 (→ DC-C04 / PM029):** whether Datum adopts Git itself as the transport substrate is a dependency decision for the owner (PM029) — flagged, not asserted here; the semantic-merge layer is first-party regardless.
- Distributed writer coordination EXTENDS the single-writer boundary PWO defines. The single commit path (PM001 :316-333) is enforced today under the engine's LOCAL `ProjectWriteLease` (PWO), whose local contract is itself parked at its owner gate (PWO-C03, O1-R unresolved). A multi-site distributed writer-coordination model therefore does not merely add to the canonical commit path — it extends a boundary whose LOCAL form is not yet owner-closed. **CONSTRAINT C-DVCS-3 (cross-lane dependency, → Q6):** distributed writer-coordination presupposes and sequences AFTER the PWO single-writer boundary's resolution (PWO-C03); DC-C02 specification and the DC-C04 owner gate must treat the PWO→DC ordering as an explicit prerequisite, not an implicit cross-reference. This records a real dependency — it is NOT a shrink; the distributed requirement stands.

## §C — RESEARCH-LOCAL-FIRST: offline / air-gapped / high-latency, no central dependency
**Prior art (planning altitude):** the "local-first software" tenets (full function offline; the local copy is the primary authority; sync is a background merge, not a precondition; no required central server/cloud); CRDTs and operation logs as convergence mechanisms for offline divergence; delay-tolerant / store-and-forward exchange for intermittent and air-gapped links (sneakernet bundles).
**Datum constraints (reconciled against current governed state):**
- **CONSTRAINT C-LF-1 (the owner's hard requirement):** full local functionality must NOT depend on a central service, AI, presence or connectivity (bound :41-42). Datum's architecture already favors this — the engine + resolver + journal are local; there is no required cloud authority; AI is optional (CLAUDE.md ethos: manual-first, AI never a hidden authority). This tenet is NATIVE to Datum, not bolted on. **Scoping (no-shrink precision):** local-first-no-central-dependency being native does NOT imply the distributed-collaboration capability is met — it satisfies only the no-central-dependency tenet. The multi-site merge/coordination DISTANCE (F-LF-1 single-machine lease, C-LF-2 divergent-journal reconciliation, F-CAD-1 conflict taxonomy) remains the owner's full requirement; "native/already favors" must not be mis-read downstream as distributed-READINESS.
- **Offline divergence + reconvergence:** two disconnected editors each advance their local journal; reconvergence is a semantic merge of the two journals (§B), not a textual sync. **CONSTRAINT C-LF-2:** divergent local journals reconcile by replaying/merging typed Operations with identity reconciliation, preserving each branch's provenance.
- **Air-gapped / delay-tolerant exchange:** a self-contained, inspectable, signed bundle (the deterministic shards + journal + provenance) that can cross an air gap and be verified + semantically merged on the far side. Ties to §D signed exchange + PM034 controlled release.
- **FINDING F-LF-1 (no-shrink, explicit):** the current engine's write coordination is a LOCAL single-machine `ProjectWriteLease` (PWO, parked at PWO-C03) — it coordinates one machine's writers, NOT multi-site distributed divergence. That is a measured DISTANCE from distributed-ready, recorded here as a CONSTRAINT/FINDING to reconcile at DC-C02+ — **NOT** a reason to reduce the owner's distributed-product requirement. The requirement stands; the engine grows to meet it.

## §D — RESEARCH-CAD: collaborative CAD/EDA + PDM/PLM prior art (compare, don't copy)
**Prior art (planning altitude; compared, not copied — PM029):**
- EDA + Git today (e.g. KiCad + Git): text/S-expression files under Git with TEXTUAL merge — the exact assumption §B rejects for authored design state; works for diffing/history but not safe semantic merge of connectivity/placement.
- Check-in/check-out LOCKING PDM (classic Vault-style): pessimistic locking avoids merge conflicts by serializing edits — maps to Datum's existing single-writer lease at local scope, but does not solve offline divergence (locking needs the lock authority reachable). **CONSTRAINT C-CAD-1:** pessimistic locking is insufficient alone for the owner's offline/air-gapped requirement; semantic merge is required for divergence that locking cannot prevent.
- Branch/merge + semantic-merge CAD (e.g. managed-cloud MCAD/EDA with server-side branching): branching + managed merge with permissions/roles — the capability shape Datum needs, but server-mediated; Datum must achieve the semantic-merge capability WITHOUT a required central service (§C C-LF-1).
- PDM/PLM controlled release + provenance + signed exchange: revision/status/release state machines, approvals, signed/controlled documents — maps to PM034 (revision/status/release/issued identity) + PM001 provenance. **CONSTRAINT C-CAD-2:** distributed collaboration consumes PM034's controlled-release + issued-record authority without competing with it (same consume-not-redefine discipline as ADS-C02 §G); a signed exchange bundle carries provenance + the governed release state, never a rival lifecycle.
- Permissions: team roles / access control on who may propose vs commit vs release — maps to PM001's Proposal-vs-direct-commit split (an agent/remote peer PROPOSES; acceptance is governed). **CONSTRAINT C-CAD-3:** remote-peer changes enter as Proposals subject to the same acceptance/permission governance as any proposal, never as unmediated commits.
- **FINDING F-CAD-1 (→ prerequisite):** the exact semantic-merge conflict taxonomy (which Operation pairs commute, which conflict, how identity splits/merges reconcile) is design work beyond this inventory — flagged as a DC-C02 specification target + a prerequisite for any conflict-resolution claim, not resolved here.
