## §B — What a figure may be in C02 (the honest-states rule)
Because no benchmark runs (marker :237), each number below is tagged:
- **PROPOSAL (five specified):** a drafted target with its PM051 five stated; where supporting evidence is not yet collected, that is named explicitly as a **required-at-C03 baseline input**, not implied as existing.
- **METHOD/PROTOCOL choice:** a measurement-protocol-bound value chosen by a stated principled rationale (e.g., nearest-rank percentile method) — a measurement-protocol bound, a distinct TYPE from a responsiveness requirement (GP-051-05).

Each budget also carries its **requirement TYPE** (responsiveness / resource-admission guard / regression trigger / measurement-protocol bound) — these are not interchangeable (GP-051-05).

## §C — Timing boundary 1: INPUT-TO-PREVIEW (TYPE: responsiveness)
- **Boundary definition (end-to-end, reproducible):** START = the input event is received by the application (e.g., keypress/pointer commit of an entry); STOP = the resulting preview is OBSERVED on the display (presented frame), not a render-only or GPU-only slice. Per GP-051 "GPU execution is not input-to-observed-display responsiveness" — this budget is input→observed-preview end-to-end, never a render-only slice relabelled.
- **Proposed target (PROPOSAL, unratified):** p95 input-to-preview ≤ **one 60-Hz frame = 16.67 ms**. PM051 five: *derivation* = the foundation handoff design proposal (handoff.md:154-158), a perceptual frame-cadence argument, NOT a Datum measurement; *representative evidence* = **NOT yet collected** — a required-at-C03 baseline campaign on the reference host over the MC-* and (once sized) scale fixtures; *configuration* = reference host (C01 §G build/hardware/display/filesystem/env); *limits* = no measurement yet, display cadence assumption (60 Hz) is itself a config variable, reference-host≠all-hardware; *product rationale* = a preview within one frame reads as immediate to the user. **State: unratified PROPOSAL; blocking status owner-reserved at NWB-C03.**
- **Percentile:** p95 primary (responsiveness tail that users feel), p99 reported alongside as the worse-tail; nearest-rank method (GP-051-02). The p95 CHOICE is itself a number with rationale (responsiveness requirement type) — not interchangeable with a resource guard.

## §D — Timing boundary 2: COMMIT-TO-DURABLE completion, INCLUDING ACTUAL I/O (TYPE: durability)
- **Boundary definition:** START = the commit() of a typed OperationBatch (PM001 single commit path); STOP = **durable** completion — the PM000D sequence of journal append + flush + atomic rename + **directory fsync** (:374-393). This is commit-to-DURABLE, NOT commit-to-in-memory; the fsync/durable-write cost is INCLUDED (the bound's explicit "including actual I/O"). Excluding fsync would understate the budget and is disallowed.
- **Proposed target (PROPOSAL, unratified):** p95 commit-to-durable ≤ **100 ms**. PM051 five: *derivation* = the handoff design proposal (:154-158), NOT a measurement; *representative evidence* = **NOT yet collected** — required-at-C03 baseline, and MUST include real durable I/O (filesystem/fsync semantics per C01 §G); *configuration* = reference host incl. storage class + filesystem flush semantics (fsync cost is storage-dependent — a config variable, reference-host≠all-hardware); *limits* = no measurement; durable-I/O cost varies by storage/fs; *product rationale* = a committed edit persists within a human-tolerable pause. **State: unratified PROPOSAL; owner-reserved at NWB-C03.**
- **Percentile:** p95 primary + p99 tail, nearest-rank; TYPE = durability (distinct from the §C responsiveness type).

## §E — Measurement method (cold/warm, samples, percentile, ceilings, exclusions, noisy-run)
- **Cold vs warm (defined):** COLD = first run after process start with OS page cache / filesystem cache / allocator in a defined cleared state; WARM = steady-state after a defined warm-up count with caches populated. Both are measured and reported separately; the preview responsiveness budget (§C) applies primarily to WARM steady-state interaction, the commit-to-durable budget (§D) is reported for BOTH (cold dominated by first-I/O). Rationale stated; which the budget binds is an NWB-C03 owner decision.
- **Samples (N) — PROTOCOL requirement, exact value a campaign parameter:** N must be large enough for a stable nearest-rank p95/p99 with reported variability (GP-051-02), with a **finite collection/stop limit pre-stated** before any future entry (no retries-until-green). The exact N is a baseline-campaign parameter fixed at collection time with its stop limit — **not an invented round number here**; the REQUIREMENT (stability + finite stop) is specified.
- **Percentile calculation:** nearest-rank (GP-051-02), p95 primary + p99 reported; no interpolation that hides tail. (Method/protocol choice with rationale.)
- **Resource ceilings (CPU/memory/other):** **UNDECIDED** — no measurement exists to justify a ceiling, and a ceiling is a resource-admission-guard TYPE requiring its own basis; proposed as a required-at-C03 item, not asserted here (GP-051-03).
- **Exclusions + noisy-run handling (principled, pre-stated, NO variability-hiding):** a run is INVALID only for a pre-stated, principled reason (e.g., a detected competing system load above a declared threshold, an instrumentation fault, a thermal-throttle event) — declared BEFORE collection, never a post-hoc favorable-run subset, adaptive sweep, universal overhead subtraction, or pooled summary that hides variability (GP-051-02). Every excluded run and its invalidity reason are PRESERVED and reported, not silently dropped. The exclusion thresholds are themselves numbers → stated with rationale or UNDECIDED pending the campaign.

## §F — Proof artifact fields (what a future proof run records; first-party)
Per GP-051-02, each proof artifact records at minimum: nearest-rank **p95 and p99**, **N**, **max**, full **configuration** (build/hardware/display/filesystem/env per C01 §G), **validity** (and any exclusions with reasons), **variability** (spread/stddev or inter-quartile), **limitations**, plus **fixture id**, **cold/warm** label, and **timestamps**. The artifact is a first-party JSON record (no benchmark-library format). It states whether each figure is a proposal or (post-C03) a ratified threshold — never auto-promoting.

## §H — Regression comparison (first-party, no benchmark library)
A later proof run is compared to the proposed budget and to a prior proof artifact by comparing the stored **nearest-rank p95/p99** (and reported variability) first-party — a direct comparison of recorded percentiles against the (post-C03) ratified threshold and against the previous artifact's percentiles. **No benchmark library** (criterion/pytest-benchmark/etc.) is introduced (bound :237); any such dependency is a PM029 owner decision, not assumed. A regression is flagged when a later run's percentile exceeds the ratified threshold or regresses beyond a pre-stated tolerance against the prior artifact — tolerance itself an NWB-C03 item.

## §I — Refusal / failure behavior (honest)
When a budget is exceeded or a run is invalid, the future proof producer **reports/refuses explicitly** — it never silently passes a failing run nor silently drops a bad run. A budget exceedance is reported as a flagged result (not a crash); an invalid run is recorded with its invalidity reason and excluded per the §E pre-stated policy (preserved, not hidden). Consistent with the PM000D atomic-refusal discipline (pending/mismatch never silently published) and the no-variability-hiding rule. Before C03 ratification, an exceeded PROPOSAL is NOT a product defect (GP-051-01 posture) — it is evidence for the owner's ratification decision.
