## Why existing signoff has not protected ordinary use

1. **The demonstrated journey has sometimes differed from the user's journey.** The retained testing-chain audit documents synthetic/prepared inputs and assisted navigation, with important ordinary entry and persistence steps excluded. Later real-input repairs deserve credit; the original scope mismatch remains a lesson, not a claim those fixes are absent.
2. **Intermediate success has been mistaken for visible success.** The [first-edit record](../workflow-delivery-rollout/user-edit/first-edit-runtime-qa.json) explicitly withdrew a moving-preview claim because prepared geometry changed while the displayed object did not.
3. **Regression and conformance are different.** [check_gui_visual_parity.py](../../../scripts/check_gui_visual_parity.py) states that it compares an interim app golden with the app, not with the HTML prototype. [check_gui_reference_capture.py](../../../scripts/check_gui_reference_capture.py) checks reference availability/validity. Neither substitutes for reviewing matched application/prototype states. Historical “placeholder” prose in these scripts is not current application-capability evidence.
4. **Technical feasibility and usable task design have been conflated.** An operator who knows the Entity/Part/Map sequence can complete the 0603 example. This does not prove that a designer can discover and perform footprint assignment unaided. Here an existing audit finds a design problem even where target and Rust agree.
5. **Task closure has broader connotations than its proof.** Practical-PCB acceptance explicitly excludes manufacturing readiness, release GUI, general ECO and full qualification. Those exclusions must remain visible when discussing overall software readiness.
6. **Error reporting prevents diagnosis.** The screenshot's “edit not confirmed; no retry was sent” is a generic journal-reconciliation wrapper ([native_edit_client.rs](../../../crates/gui-protocol/src/native_edit_client.rs), around line 625). It does not identify the validation rule. Truncated feedback leaves the designer unable to recover and prevents a reliable diagnosis from the screenshot alone.

The evidence supports a mixed diagnosis. It does not support “all specifications are too basic,” “all tests are useless,” or “agents cannot build software.” Some intent is clear and incorrectly implemented; some intent itself produces an awkward workflow; some capabilities are unfinished.

## Build → test → fix → signoff, using existing machinery

### 3. Test the actual task and its boundaries

Use a provenance-verified real project copy and the actual installed library input. The normal test starts where the designer starts: public New/Open, component search, properties and visible commands. Do not pre-create the very Part/map/binding being tested. Synthetic/unit fixtures may supplement negative boundaries but do not replace representative delivery proof.

Use [run_native_qa_isolated_input.py](../../../scripts/run_native_qa_isolated_input.py) with [StartupQA](../../../scripts/prove_native_project_startup_gui.py). They already provide isolated input, compositor, candidate bindings and cleanup. Never launch automation on the owner's live display. Existing QA013 driver is interactive and records observations; its raw `REVIEW_PENDING` result is not an automatic assertion of semantic success.

For each affected workflow, inspect these four kinds of evidence together:

- **Visible behavior:** pointer/keyboard entry, selected target, focus, preview, result, cancel, complete error and useful next action. Captured screen must match the state under discussion.
- **Design correctness:** exact intended identities, connectivity, geometry and preserved unrelated objects, observed through canonical readback. Pixels alone do not prove pin/pad net correspondence.
- **Persistence:** intended history boundaries, exact Undo/Redo, acknowledged Save, terminate and ordinary cold reopen without an undocumented focus/Fit rescue. If recovery requires a visible supported action, record that limitation rather than claim automatic healthy reopen.
- **Visual fidelity:** native and HTML views of the relevant normal, empty, error and constrained-size states, plus DOM/CSS review where required. Identify a prototype defect separately from a translation defect. No new universal viewport or timing threshold is invented here.

The ready-made Preferences example below is a reusable shared-UI check, **not** a schematic or whole-product test:

```bash
python3 scripts/run_native_qa_isolated_input.py --output /absolute/fresh/evidence/path --scenario preferences --binary-dir /absolute/candidate/binary/directory
```

The output directory must be fresh. Review its images before any visual signoff. Owned Weston evidence does not certify the owner's KWin desktop. Menu/dialog capture failure such as `dat-lwhd` is a transport/evidence blocker for that observation, not proof that the product action failed.

### 4. Fix and repeat the affected checks

Preserve the original failure. Repair the responsible production path, preferring a shared service when the defect affects multiple editors. Repeat the failed step plus its affected persistence/safety/visual checks. Reuse unchanged proof. Do not regenerate a golden to bless a disagreement with the prototype. Codex does not edit protected HTML; its owning lane reconciles agreed target changes.

Continue routine corrections under the recorded grant. An ordinary failed test is feedback to the implementer, not a reason to send the owner another approval request. Stop only the affected action for an actual authority, safety, ownership, environment or independent-review blocker, and record its remedy.

### 5. Independent signoff against the frozen outcome

The reviewer must be distinct from the implementer and must review the exact candidate. Record the reviewer identity, observations and verdict in the same task, referencing raw evidence once. Source review alone cannot sign off a visible workflow. A manager who materially designed or implemented a candidate cannot be its independent reviewer.

Use plain outcome labels: **passed at stated scope**, **failed**, **blocked before execution**, or **not tested**. Keep them distinct from **implemented** and **landed**. A test count, a screenshot's existence, an accessible-node count, a digest, or a tracker closure is not product signoff.

PM accepts proven bounded delivery within the appointment. Literal human observations and explicit owner-only acceptance remain separate where already required; routine owner use is voluntary feedback. The owner is not responsible for supplying routine reproduction, regression execution or documentation.

### 6. End-to-end release decision

At a designated stable candidate, combine a real fresh-project journey with an existing symbol-only project journey through the required supported scope: schematic → physical assignment → board editing → checks → save/cold reopen → manufacturing. Include an ordinary correction cycle, not only initial creation. Keep unsupported operations visible. Reuse unaffected stage evidence but do not claim a newly executed uninterrupted journey unless it was actually executed.

The reviewer reports stage outcomes and concrete remaining blockers. PM/owner makes only the acceptance decision covered by the existing authority. Full qualification remains separate; a narrower development build may be useful without pretending the complete product is ready.
